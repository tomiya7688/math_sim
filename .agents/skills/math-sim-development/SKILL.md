# math_sim 開発手順

このskillは、複数言語の実装・設計・レビューで読む範囲を抑え、別エージェントへ安全に作業を渡すときに使う。

## 作業を始める

1. 依頼を `Goal`（達成すること）、`Required`（制約・守る契約）、`Acceptance`（完了の判定）に短く整理する。不明点があっても独立して進められる調査は続ける。
2. `git status --short` と現在のブランチを確認し、既存の変更を保持する。追跡先があれば `git fetch` してahead/behindを調べ、遅れていれば未コミット変更を保全して先に同期する。安全に同期できない場合はリセットせず、同期できない理由を示して止める。変更前に対象 Issue と依存関係が分かる場合は確認する。P0は緊急対応専用。
3. オープンPRがないか確認する。ある場合は対象差分、最新headのCI、レビュー指摘を確認し、問題があれば修正して再確認する。レビュー担当と修正担当は固定しない。問題がなく必須チェックが通ったらマージし、ベースブランチへの反映を確認してから次の開発へ進む。状態を確認できないときは完了扱いにせず報告する。
4. [コンテキストマップ](../../../docs/development/context-map.md)から担当領域を選び、`rg --files` / `rg -n` で対象ファイルと契約を探す。見つけたファイルの必要な部分だけを読む。
5. 次の項目がそろったら探索を止め、実装またはレビューへ進む: 対象コード、正本となる契約・設計、受け入れ条件、適切な確認方法。

## 情報の扱い

- ユーザー依頼と対象Issue、仕様・スキーマ、現行コードと既存チェックを根拠として扱う。ビルドログや生成物は必要な場合だけ読む。
- 既存の手順・ツールを先に探し、同じ説明や自動化を重ねて作らない。コンテキスト削減で正確さや必要な証拠を省かない。
- `ai-context-reducer` のツールが利用可能な環境では、対象に合う既存ツールを任意で使ってよい。存在しない場合は `rg` 等で進められること。特定の別リポジトリの絶対パスを前提にしない。
- 選んだ確認方法が何を証明し、何を証明しないかを区別する。テスト、ビルド、実画面の操作、CIは別々の証拠として報告する。

## 他エージェントへ委譲する

委譲時は、受け手がこの文書とコンテキストマップを参照できる前提で、次を短く渡す:

- Goal / Required / Acceptance
- ベースとなるブランチまたはコミット、作業範囲、所有するファイル
- 変更してはいけない隣接領域と共有契約
- 実行する確認方法と、結果の報告形式

同じファイルを複数エージェントに同時編集させない。独立したファイル領域へ分け、統合担当が契約・差分・確認結果をまとめる。長期・複数段階の引き継ぎだけ、[CONTEXT_PACKテンプレート](../../templates/CONTEXT_PACK.md)を一時利用し、仕様本文を貼り直さず正本へのリンクを残す。

## Pull Request運用

- リモートへ反映するときは作業ブランチを使い、Pull Requestを作成または既存PRを更新する。ベースブランチへ直接pushしない。
- 先行するオープンPRがあれば、次の開発へ移る前にそのPRをレビューし、問題があれば担当を問わず修正・再確認する。問題がなく必須CIとレビュー条件が満たされたPRはマージし、ベースブランチの更新を確認する。
- GitHubの状態を取得できない場合、PR確認・レビュー・マージ済みとは報告しない。

## 完了報告

変更ファイル、受け入れ条件に対する結果、実施した確認とその範囲、未確認事項、次の依存作業を簡潔に報告する。実行していない確認を成功扱いにしない。
