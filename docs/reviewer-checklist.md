# Pull Request レビューチェックリスト

受付判定と承認判定を分ける。詳しい基準と変更別の必要情報は[レビュー基準](review-policy.md)を参照する。

## 受付判定

- [ ] 目的・期待動作・変更範囲と関連Issueまたは理由が分かる
- [ ] 影響する層・モジュールが分かり、必要な契約・README・設計資料へのリンクがある
- [ ] 実施した検査の対象headと結果が示され、未実施・未確認も明示されている
- [ ] 変更種別に応じた数理モデル、schema互換性、README、ライセンス等の情報がある
- [ ] 新規module等のREADMEに必須節があり、責務・依存方向・実行/テスト方法を読み取れる
- [ ] READMEの相対リンク先が存在し、READMEとJson-like Comment Outsの責務説明が一致する
- [ ] 無関係な追加資料を一律に求めず、対象外条件には理由がある

不足がありレビュー開始できない場合は **REVIEW_BLOCKED** とし、不足項目と修正先を示す。

## 実装確認

- [ ] 新規production宣言のJSON-like comment blockに宣言名・必須キーがあり、説明が実装と一致する（該当時）
- [ ] 必須CI・自動検査は対象PRの最新headで成功し、欠落・未実行を成功扱いしていない
- [ ] 実装が共有契約・設計と一致し、層の依存方向を破っていない
- [ ] 正常系、入力検証、エラー・異常系を必要な範囲で確認した
- [ ] 変更したREADME・仕様・schema・コメントは実装と一致する
- [ ] 再現性・配布境界・依存ライセンスへの影響を確認した

問題を確認した場合は **REVIEW_REJECTED** とし、ファイルや行、再現条件、対応内容を具体的に示す。

## 人による判断

- [ ] 数理・物理・科学モデルの式、単位、前提、境界条件と検証根拠を確認した（該当時）
- [ ] CIでは判断できない設計・操作性・安全性の論点を確認した（該当時）
- [ ] 未解決指摘がなく、対応後の差分を再確認した

受付情報と必須検査がそろい、人による判断へ進める状態を **REVIEW_READY** とする。数理的妥当性など人の判断が残る場合は **REVIEW_REQUIRED** として論点を明記する。承認または変更要求はこの受付状態とは別に記録する。`REVIEW_READY`は承認済みを意味しない。
