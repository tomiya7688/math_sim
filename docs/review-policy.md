# Pull Request レビュー基準

この文書は「レビューを開始できる情報がそろっているか」と「変更を承認できるか」を分けて定義する。PR提出者は変更に該当する情報を示し、レビュアーは[レビューチェックリスト](reviewer-checklist.md)で確認する。Issue #199のREADME検査は必要なREADMEの有無・品質を検証する。レビュー受付条件全体のCI集約はIssue #201が扱う。

## 判定区分

- **REVIEW_BLOCKED**: 受付に必要な目的・範囲・証拠・契約情報が足りず、実装レビューを始められない。
- **REVIEW_REJECTED**: 確認により不具合、必須検査の失敗、または契約違反が見つかった。修正後に再確認する。
- **REVIEW_REQUIRED**: 必須情報と機械検査はそろっているが、数理的妥当性・安全性・設計判断など人の判断が残る。
- **REVIEW_READY**: 受付情報がそろい、必須の機械検査に根拠がある状態。承認済み・マージ可能を意味しない。

## レビュー受付条件

すべてのPRで以下を確認できること:

- 目的、変更範囲、期待する動作、および関連Issueまたは理由
- 影響を受ける層・モジュールと、変更していない主要な隣接領域
- 実施したテスト・静的解析・ビルド等の結果。未実施の項目は「未実施」と理由を記載する
- 対応するREADME、設計資料、スキーマ、ユーザー向け説明へのリンク。更新不要ならその理由

該当する変更には以下も必要:

| 変更 | 受付時に必要な情報 |
| --- | --- |
| 新規module / engine / runtime / domain / demo / CLI / shared subsystem / 独立tool | 対象README。責務、境界、構造、実行・テスト方法、該当する入出力と代表的なエラーを示す。基準はIssue #199に従う |
| 公開Command/Response、schema、保存形式 | 旧版との互換性、versioning、golden/example変更、利用側と移行への影響 |
| 数学・物理・科学モデル | 使用する式、記号と単位、前提・境界条件・近似、検証方法・根拠・許容誤差。モデルの意味的妥当性は人の確認事項として残す |
| 第三者ライブラリ・データ・アセット | 出典、version、license、NOTICEや配布への影響 |
| ユーザー操作・画面・配布構成 | 利用者向け説明、対応README、必要なら画面・配布物の確認結果 |
| リファクタ・内部変更 | 既存のどのテスト・契約が振る舞いを保つ根拠か。新しい文書が不要なら対象範囲を示す |

小さな文書修正にシミュレーション検証書を求めるなど、変更と無関係な条件を一律に要求しない。機械的に確認できない場合は、実施者の申告だけで実行済みと扱わず、未確認であることを明記する。

## 承認条件

受付可否とは別に、承認前に該当する項目を確認する:

- 必須CI・自動検査が対象PRのheadで成功し、未実行・欠落を成功扱いしていない
- GUI / Application / Domain / Runtime / engine adapter等の責務と依存方向が保たれている
- 実装、仕様、README、schema、宣言コメントが一致し、異常系とエラー処理も妥当
- 数理・科学モデルは式、単位、仮定、境界条件、検証根拠をレビューし、CIだけで正しさを宣言していない
- 再現性が必要な結果はseed、solver、入力、version、環境などを追跡できる
- 配布物のruntime境界、第三者ライセンス、NOTICE要件が満たされている
- 対象PRへの未解決の重大指摘がなく、差分と確認結果が一致している

機械判定と人による意味判断を分ける。必須チェックが成功しても、それだけで科学モデルの妥当性や承認を意味しない。

## 可読性・命名・エラー処理

変更行だけでなく、周辺の責務を理解するのに必要な範囲を読んで次を確認する。

- 関数・メソッド名から主要な処理が分かり、`run`・`process`・`calc`のように文脈なしで曖昧な名前を避けている
- 変数名から値の意味が分かり、誤解しやすい値では型・表現・単位・状態を示している（例: `timeoutSeconds`、`requestJson`、`isSimulationRunning`）
- 1回しか使わない別名、重複state、未使用変数など、理由のない一時変数を増やしていない。意味のある処理段階を表す変数は許容する
- 閾値や制約値はnamed constant・enum・設定として名前を付ける。`0` / `1`、添字、式の意味から明らかな定数は文脈上自明なら許容し、説明できないliteralは指摘する
- error / Result / 戻り値を確認し、file・parse・subprocess・timeout・cancellation・domain failureを握りつぶさず、適切な層へ伝える
- bool値を `== true` / `== false` と比較せず、否定の意味も読み取りやすく表す
- 到達不能処理、不要な代入、常に同じ結果になる条件などを確認する
- `docs/commenting.md` の構造化コメントがある場合、責務・処理の記述が宣言と実装に一致している

## 自動検査の範囲

CIは、機械判定できる範囲で未使用名、未定義名、冗長なbool比較を失敗にする。意味のある定数か、命名が責務に合うか、失敗時の振る舞いが適切かは人が判断する。Python以外の言語がproduction対象に加わる場合は、その言語のlinterとerror/result確認をCIへ追加する。自動化されていない項目をCI合格と報告しない。

## 変更種別ごとのチェックリスト

PRテンプレートでは変更種別を選択し、該当する条件だけを記入する。複数の種別に当たる場合は複数選ぶ。どの条件にも該当しない変更は「該当なし」と理由を記載する。レビュアーは[レビューチェックリスト](reviewer-checklist.md)を使用する。
